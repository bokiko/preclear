<flagged_assumptions>
This plan takes gaps 2 and 3 of 03-VERIFICATION.md and re-proves HARN-09 after plan 03-07. Items specific to it:

- FA-1 (the order of the two streams in the fake): the review says to make the scripted claude return standard output then standard error. The real Bash tool merges the two streams as the process writes them, and the stub writes its brand line to standard error before it prints anything, which is why the real result begins with the brand line. A plain concatenation of standard output and then standard error would put the brand line last and would not reproduce the defect. This plan therefore merges the streams in time order (standard error redirected into the same pipe), which is what the real tool result is, and pins the first line of the fake's result to the brand.
- FA-2 (the status fact keeps its name): the key status_begins_with_session and the filed label status-begins-with-session are kept so that the filed set, the comparer and the checklist do not change shape. The meaning is now "the helper's session line is among the first five lines". The filed baseline, rerun-2026-10-29-claude-sonnet-5-5, records no for it because of the earlier rule; a future run records yes. Whether the baseline needs a note or a refile is bokiko's decision (03-VERIFICATION.md); this plan adds neither, and the README states the difference in one sentence.
- FA-3 (what is clean): a stage record is clean when its problem is the empty string and its evaluation is pass, which is exactly what the live path requires before it goes on (result.ok and an evaluation of pass). A record that lacks either key is not clean (fail closed). The chain-level fact that s2 must exist is not added: the live path reaches the filing only after s2, and an interrupted run holding only a clean s1 record can still be refiled. That observation is outside the disposition and is listed under "Observations, not planned".
- FA-4 (the exit code of a missing deny list): file_row and file_skipped return exit 15 (SCANNER_ERROR), the code the row already uses when the sanitizer or its entries cannot be built; the filing cannot be trusted, which is that code's meaning. The text is fixed and holds no value.
- FA-5 (the promote opt-out): the keyword is allow_default_deny and defaults to false. The promote command line passes true because it has no sanitizer; its default entries carry no login by design (the Phase 2 decision), and a stranger running it by hand knows that. The two existing test call sites that rely on the default pass the opt-out explicitly.
- FA-6 (the leftover sentence in the 03-06 summary): the verification lists a sentence in that summary (unobserved question 2) that still called the cumulative-cost question unsettled. On the file as it stands now, that sentence already says the question is settled by the code review, so there is nothing to edit; the executor only reads it once to confirm. The 0.2723 figure rests on the review and the pinned fixture test, and from this plan on also on the consistency lines a future usage.txt carries.
- FA-7 (the README is edited once): this plan's last task edits the harness README for both plans 03-07 and 03-08. test_readme.py bars cost figures, absolute path fragments and email addresses from it, so the new text uses none.
- FA-8 (the re-proof is a test class, not a paid run): the verification asks that HARN-09 be re-proved at zero tokens.
