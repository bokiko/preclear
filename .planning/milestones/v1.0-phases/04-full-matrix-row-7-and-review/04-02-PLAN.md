<flagged_assumptions>
Plan 04-01 holds the phase-level audit, the plan map and FA-1 to FA-11. Items specific to this plan:

- FA-1 (stop filing is plan 04-03): this plan lets the loop continue after a stopped row, but a stopped row still files nothing until plan 04-03 adds the `STOPPED-` folder; between the two plans a stop returns its Phase 3 exit code and no folder, and no paid wave runs in that window.
- FA-2 (an engineering choice, stated): filing failures and refusals (14, 15, 16, 17, 18) end the invocation instead of continuing, because a leak, a scanner error, a name collision or a budget stop may apply to every later row too and continuing would spend before the cause is understood; row-level outcomes (10, 11, 19) continue, as D-02 requires.
- FA-3 (an engineering choice, stated): the `matrix` ledger scope exists because the clean-clone run reuses the owner's harness home (plan 04-19, FA-4 of plan 04-01) whose ledger already holds Phase 3 row 1 lines; the folder name stays bare because the carried-forward evidence name is `rerun-<date>-<model>`.
- FA-4 (unobserved): the result subtype of a turn-limit or cap hit on 2.1.310 is not known (Phase 3 summary, unobserved question 3); the classification added in plan 04-03 keys on the text of the subtype and is checked against the first real stop.
</flagged_assumptions>

<objective>
Turn the single-row driver into one that can run a campaign: a labelled dated folder, attempts that never collide, a date override for retries, a multi-row loop that keeps going after a skipped or stopped row, an exit code that never reads as success when something was skipped or stopped, and a per-invocation budget that stops before a row would take the invocation past it. Ledger identities become campaign- and attempt-scoped so reruns, waves and the clean-clone matrix are legal without typed authorizations.

Purpose: D-01 (one go word and one budget per wave), D-02 (the wave goes on), D-03 (attempt folders), D-12 (order) and RERUN-02 (`--all` runs every entry); RESEARCH findings 3 and 4.
Output: scoping and naming functions in `pc_rows.py`, the loop and flags in `pc_matrix.py`, the budget parser in `pc_flags.py`, scoped spend identities in `pc_row1.py`, `test_driver_matrix.py`, updated budget literals in two Phase 3 test modules and README text.
</objective>
