<flagged_assumptions>
The ROADMAP probe ledger and the reason Phase 2 was planned as eight plans are in plan 02-01. This plan is the single gap-closure plan for the one gap in 02-VERIFICATION.md (truth 6, EVID-02 and EVID-03 PARTIAL). Items specific to it:

- FA-1 (the twin rule must run on the hooks' engine): the commit hooks run gitleaks, whose regular-expression engine has no lookahead and no lookbehind. The review's suggested fix for CR-02 uses a lookahead, which that engine cannot compile, and the parity test requires the Python strings to be byte-identical to the TOML. The tightened mirrored rules therefore end in a consuming negated class (any character that is not a name character, or end of text). Lookarounds appear only in the two Python-only rules, which have no TOML twin. Verified while planning: the tightened TOML compiles under the installed gitleaks 8.30.0, flags every boundary shape in a scratch repository, leaves the full-history scan at exit 0, and leaves `sh scripts/test-hooks.sh` at 29 PASS and exit 0 in a faithful copy of this repository with the change committed.
- FA-2 (JSON escapes): a JSON string holds a line break as a backslash plus n. The boundary escapes for the login are the letter escapes that stand for a control character (n, r, t, b, f). The quote and backslash escapes already pass the existing word lookbehind because the character before the login is not a word character. An escape that is itself preceded by a backslash is ambiguous (an escaped backslash followed by a letter, or an escaped backslash followed by a real escape); the lookbehind is deliberately not made smarter, so an ambiguous case is replaced, never kept. Over-replacing is the safe direction for a privacy layer.
- FA-3 (where the login joins the gate): the login is added to Sanitizer.deny_entries(), the list the spike driver hands to the gate for what it sanitised. It is not added to pc_leakgate.build_deny_entries(), which the gate CLI and promote's default use, because bokiko's login is also his public alias and appears in committed prose (the spike findings), so a gate that refused it everywhere would refuse the committed corpus. A caller that sanitised with a Sanitizer passes sanitizer.deny_entries() to promote (recorded in the deferred note for the Phase 3 runner).
- FA-4 (a login that names no person): a login that occurs inside one of the fixed tokens (user, home, host, repo, root as in the auto-memory token, and so on) is not added to the gate's entries, because the gate matches entries as plain substrings and would then refuse every sanitised file for holding its own token. The sanitizer still replaces the bare word. Such a login identifies nobody.
- FA-5 (a repository-less tree): the self-test shim states that a downloaded archive works, and an archive has no .git. The local deny list lives in .git/info, so a tree with no .git entry in itself or any ancestor has no local deny list by definition: no entries, no error. Every other failure to establish where the list lives (a root that is not a folder, git missing, git timing out, a non-zero git exit while a .git entry exists, an empty answer) is ScannerError and exit 15. This is the review's fix with one deterministic exception for the no-repository case, so that the stranger path keeps working.
- FA-6 (dash-slug rule): home-path-dash-slug keeps its closing-dash shape. It has no delimiter list to replace (the closing dash is part of the shape), and loosening it to match a slug with nothing after the name would flag ordinary hyphenated words that start with the folder word. It still matches every slug followed by any text. Recorded in the deferred note.
- FA-7 (Python-only rules stay Python-only): CONTEXT defers adding the superuser and Windows-style home shapes to the gitleaks rule list to Phase 4. This plan tightens the boundary of those two shapes in the Python gate only and does not add them to the TOML.
</flagged_assumptions>

<objective>
Close the one gap the Phase 2 verification found: the privacy layer's identifier matching does not understand JSON escapes, so a stranger's real run could reach `tests/evidence/` with the login name or a home path still in place. This plan makes the sanitizer's whole-word login match treat a JSON letter escape as a boundary and gives the gate a login entry (CR-01), replaces the closing-delimiter lists in the gate's home-path rules and their `.gitleaks.toml` twin with a "not a name character" ending (CR-02), makes the identifier rules ASCII-only and the host suffix case-insensitive (WR-01), makes a failure to locate the deny list fail closed and tolerates a byte-order mark and padding in the deny file (WR-02), and adds table-driven boundary tests that also prove the committed fixtures still pass the gate (IN-07).

Purpose: EVID-02 (the runtime-built sanitizer must stop the login and home paths in the JSONL shape the harness files) and EVID-03 (the fail-closed gate must refuse them when anything slips past the sanitizer). Phase 3 success criterion 1 says every filed file passed the leak gate; this plan makes that statement true for the escape-shaped leaks.

Output: edits to `pc_sanitize.py`, `pc_leakgate.py`, `.gitleaks.toml`, `test_sanitize.py` and `test_leakgate.py`. No new file, no README change (no documented behaviour changes: the README documents the tokens, not the matching rules).
</objective>
